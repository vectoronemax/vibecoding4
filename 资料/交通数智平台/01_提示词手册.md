### 三条方法论

**一 · 前后端分离。** Python 产出 `data.js`，HTML 只读 `data.js`。换数据重跑脚本，网页一行不改。

**二 · 一次只加一个功能。** 加完刷新看一眼。一次让 AI 出十张图，错了你不知道错在哪。

**三 · 每一步都设可证伪的验收标准。** 这是本课最值钱的部分。
"看起来对"不是验收，"行数应该等于 302×2×17=10268"才是验收。
本手册里每条提示词下面的 **✓ 验收** 都是可以当场证伪的——对不上就停下来查，不要往下走。

# 阶段 0 · 数据验收（0.5 课时）

> **为什么先验收？** 因为数据是别人给你的。
> 别人已经踩过的坑，不代表坑不存在——只代表你不知道它在哪。
> 这半个课时是全天投资回报率最高的半小时。

## 0-1 · 让 AI 先认识这批数据

```
读 data/ 目录下的所有文件（先不要写任何代码文件），给我一张资产表：
每个文件的行数、列名、主键、以及你推断的用途。
data/commute/00_元数据.json 和 07_指标字典.csv 要逐条读完，
把里面的「已知问题」和「口径提示」原样摘给我。
最后告诉我：这批数据能支持哪些分析、明确不能支持哪些。
```

> ✓ **验收**：AI 必须主动说出"数据只有 2017 年 5–8 月，做不了多年度同比"
> 和"报告的总体平均是人口加权"。说不出来，说明它没真读元数据，让它重读。

> **教学点**：这一步最容易被跳过，也最容易翻车。
> 如果直接开做，最后会做出一个"历史对比"页却没有历史数据。
> 先知道"拿不到什么"，整个平台的设计才立得住。

## 0-2 · ⚠️ 行数断言（坑 9）

```
对 data/metro/ 的三个表做行数断言，写一个 verify.py，用 assert 而不是 print：
1. station_daily 行数 == 站数 × 日型数
2. station_hourly 行数 == 站数 × 日型数 × 小时档数
3. network_daily 行数 == 日期跨度天数，且工作日+非工作日 == 总天数
每条断言失败时的报错信息要写清楚"期望多少、实际多少"。
```

> ✓ **验收**：`604 = 302×2`、`10268 = 302×2×17`、`123 天 = 87 工作日 + 36 非工作日`。全部 assert 通过。

> ⚠️ **坑 9 · 时间字段误读**（这批数据在聚合时踩过的坑）
> 原始 12GB 表里有个 `timeslot` 字段，看起来像日内时段序号，
> **实际是跨 123 天的全局序号（0–12545）**。按 `6 + timeslot//6` 算小时，
> 会得到 **1045 个"小时"**，分时表 63 万行而不是 1 万行——**脚本不会报任何错**。
> 正确做法是用 `startTime`（`HHMMSS` 字符串）取前两位，注意它有前导零 `060000`，
> 直接整数除法会报类型错误。
>
> **通用做法**：任何"从明细汇总出宽表"的地方，行数都应该等于各维度基数的乘积。
> 把这条 assert 写进脚本，以后换数据也能自动拦住。

## 0-3 · ⚠️ 口径反算（坑 2）

```
读 data/commute/03_通勤指标宽表_2024.csv 和 09_城市背景数据.csv。
报告正文公布的总体平均是：45分钟以内 77、60分钟以上 12、平均时耗 35、
5公里以内 52、轨道800米覆盖 21、45分钟公交服务能力 48。
请分别用 (a) 45城算术平均 (b) 七普常住人口加权平均 算一遍，
输出一张表：指标、报告值、算术值、算术偏差、加权值、加权偏差、哪个口径更接近。
不要改数据，只做比对。最后告诉我结论说明了什么。
```

> ✓ **验收**：算术 79.53 / 加权 77.05（报告 77）。六项里五项是加权更接近，
> 只有「45分钟公交服务能力占比」算术更接近。结果应与 `12_校验_总体均值口径.csv` 完全一致。

> ⚠️ **坑 2 · 口径陷阱**
> 原始提取阶段做了 42 项分级均值校验，**36 项通过，6 项没过的全是"总体平均"，
> 且偏差方向完全一致**。用人口加权重算后全部复现。
>
> 结论：**报告的"总体平均"是人口加权，"分规模平均"是算术平均。**
> 这不是提取误差，是口径差异。
>
> **教学点**：**偏差方向一致 = 系统性口径问题；偏差方向随机 = 提取错误。**
> 这个判断法很通用，记下来。

## 0-4 · ⚠️ 从明细反算已知指标（坑 3）

```
用 data/commute/11_45城年龄结构_七普.csv 的年龄组明细，
反算每个城市的老龄化率（65岁及以上人口占比），
和 09_城市背景数据.csv 里的官方老龄化率逐城比对，输出最大绝对偏差。
偏差超过 0.01 个百分点的城市列出来。
另外确认一下：年龄组一共几个？和你预期的一样吗？
```

> ✓ **验收**：19 个年龄组，最大绝对偏差 **0.005 pp**。一个城市都不该被列出来。

> ⚠️ **坑 3 · 静默丢数据**
> 拼接七普年龄结构时，过滤条件写的是 `endswith("_男")`，
> 而最高龄组的列名是 `85及以上男`——**没有下划线**。
> 整个 85+ 队列被悄悄丢掉，18 个年龄组而不是 19 个。
> 不报错、`dropna()` 也抓不到、金字塔画出来还挺好看。
>
> **发现方法**：用金字塔反算老龄化率，和官方老龄化率比对。修好后偏差降到 0.005 pp。
> **通用做法**：任何"从明细汇总出总量"的地方，都要能反算回一个已知的官方指标。

## 0-5 · ⚠️ 缺失不是 0

```
data/commute/02_通勤指标长表.csv 是 1157 行，但 9 指标 × 3 年 × 45 城 = 1215。
差的 58 行是什么？请按「指标 × 年份」和「城市」两个维度分别列出缺失构成，
并对照 00_元数据.json 的「已知问题」逐条解释每一类缺失的原因。
不要填充，我只要解释。
```

> ✓ **验收**：58 = 轨道覆盖 2022 全年缺 45 + 海口/银川/西宁 2023·2024 缺 6 + 南通 2022 多项 6 + 绍兴/洛阳等 1。
> AI 必须能对上元数据里的说明。

> **教学点**：接下来做排名、算均值、画地图，这 58 个空值**一次都不能被当成 0**。
> 否则海口会变成"轨道覆盖全国倒数第一"——它压根没有轨道。

## 0-6 · 轨道数据的内部一致性

```
对 data/metro/ 做三个内部一致性校验，每项给出数值和百分比差异：
1. 工作日全网进站总量 vs 出站总量（应该几乎相等）
2. 三类客流（cin/hin/nin）之和 vs 进站总量（分类完备互斥的话应该完全相等）
3. od_pairs 总量 vs 进站总量（OD 只统计配对成功的出行，会略低）
第 3 项如果差得多，先别改，告诉我可能的原因。
```

> ✓ **验收**：进站 = 出站，差 **0.0000%**；三分类之和 = 进站，差 **0.0000%**；
> OD 前 4000 对 251 万，占进站 651 万的 **38.6%**（因为只取了前 4000 对，不是全部 OD）。
> 前两项差 0 说明聚合逻辑没问题。

## 0-7 · 外部合理性校验

```
把工作日日均进站量前 10 的站点列出来（用 stationInfo.csv 的英文站名），
和你知道的上海地铁官方客流排行做个对比，判断合不合理。
```

> ✓ **验收**：人民广场 14.6 万居首，静安寺 10.7 万、徐家汇 10.2 万、南京东路 9.4 万紧随。
> 与上海地铁公布的进出站客流排行吻合。

> **教学点**：内部一致性只能证明"算得自洽"，**外部合理性才能证明"算的是对的东西"**。
> 这是最后一道防线，任何数据产品上线前都要过一遍。

# 阶段 1 · 通勤数据层（0.5 课时）

## 1-1 · ⚠️ 先把指标方向定死（坑 4）

```
读 data/commute/07_指标字典.csv 的「指标方向」列，
把 9 个指标按 +1 越大越好 / -1 越小越好 / 0 中性 分三组列给我，
并逐个说明这个方向判断的理由。
特别解释一下为什么「通勤空间半径」是 0。
```

> ✓ **验收**：4 项 `+1`、4 项 `-1`、1 项 `0`。
> AI 要能说出：**通勤空间半径是城市尺度的描述量，不是绩效指标**——
> 北京半径 42km 全国最大，那是因为北京大，不是因为北京通勤好。

> ⚠️ **坑 4 · 指标方向**
> 不定义方向，地图配色会把"60分钟以上通勤比重最高"显示成绿色，
> 排名会把"平均通勤时耗最长"排在第一名。**图表不会报错，它只会骗人。**

## 1-2 · 生成 data.js

```
写 apps/commute/build_dashboard_data.py：
读 data/commute/ 下的 CSV，聚合成大屏数据层 apps/commute/data.js。

结构：
window.CM_DATA = {
  meta: {
    cities: [{n简称, full全称, code, cls规模下标, prov, lon, lat, pop, area, aging}],
    years: [2022,2023,2024],
    classes: ["超大城市","特大城市","Ⅰ型大城市","Ⅱ型大城市"],
    indicators: [{name, unit, dim维度, dir方向, src来源页, def口径说明}],
    reportMean: {指标: [超大,特大,Ⅰ型,Ⅱ型,总体]},   // 报告公布值，用于画参照线
    caliber: 口径提示原文, issues: 已知问题数组
  },
  values: values[指标下标][年份下标][城市下标],   // 缺失写 null，不写 0
  rail: [...], intercity: [...], interType: [...]
}

要求：
- 城市按 规模 → 2024年45分钟指标 降序排，保证所有图表默认顺序稳定
- 用下标压缩体积，不重复写城市名字符串
- 顶部写一行 schema 注释
导出后告诉我 data.js 多大、多少个指标值、其中多少个是 null。
```

> ✓ **验收**：`9 × 3 × 45 = 1215` 个值，其中 **58 个 null**。
> 浏览器控制台 `console.log(CM_DATA)` 能展开看到结构。

## 1-3 · 补三块衍生数据

```
在同一个脚本里再加三块：
1. 人口金字塔：读 11_45城年龄结构_七普.csv，pyramid[城市下标] = {m:[19组男], f:[19组女]}，
   同时算出劳动年龄人口占比(15-64岁)和抚养比。
2. 省际迁移：读 14_七普省际流动OD.csv，省质心从 data/geo/中国省级行政区_DataV.geojson 取，
   算每省流入/流出/净迁移，迁徙线只留规模前 90 的流向。
3. 综合通勤指数：把 8 项有方向的指标做方向感知 min-max 归一后取均值×100，
   dir=0 的通勤空间半径不计入。缺失值跳过，不补 0。
每块导出后报告条数。
```

> ✓ **验收**：金字塔 45 城 × 19 组、省际 OD 90 条 / 31 省、综合指数 45 城有值。
> 归一化必须是**方向感知**的：`dir=-1` 的指标要 `1-t`，否则"通勤时耗最长"会得高分。

```

## 2-7 · ⚠️ 收口时的隐藏 bug（坑 5）

```
窗口缩放时所有图表自适应 resize。
```

> ⚠️ **坑 5 · resize 隐藏的 canvas**
> 你大概率会得到这样一行代码：
> ```js
> Object.values(charts).forEach(c => c.resize())
> ```
> 它会连**隐藏面板里的图表**一起 resize。隐藏面板的 canvas 宽高是 0，ECharts 直接抛：
> `InvalidStateError: Failed to execute 'drawImage' ... width or height of 0`
>
> 必须先判可见：
> ```js
> Object.entries(charts).forEach(([id, c]) => {
>   const el = document.getElementById(id);
>   if (el && el.clientWidth > 0 && el.clientHeight > 0) c.resize();
> });
> ```

> ✓ **验收**：**切到"人口"页 → 拉伸窗口 → 切回"驾驶舱" → 打开详情页 → 再拉伸 → 返回**，
> 全程控制台零报错。这个坑只在"隐藏面板 + resize"同时发生时出现，
> 正常点两下页面根本撞不上——必须按这个顺序刻意去撞。

## 3-1 · 先探源，别急着匹配

```
先不要写匹配逻辑。读 data/metro/osm_raw.json 和 osm_st3.json，告诉我：
1. osm_raw.json 里有多少条 relation？tags 里的 ref / colour / name 分别长什么样？

```

> ✓ **验收**：`osm_raw.json` **54 条 relation**，覆盖 **18 个线路 ref**（一条线有上下行和支线多条 relation）；
> `osm_st3.json` **728 个 element**（node 365 / way 362 / relation 1），去重后 **556 个唯一中文站名**，
> 其中 **478 条**带 `name:en`；`stationInfo.csv` **302 站，全英文名**。

> ⚠️ **坑 6 · OSM 只查 node 会漏一半**（这批数据抓取时踩过的坑）
> 第一版查询写的是 `node["station"="subway"]`，只拿到 **295 站**，而上海实际有 523 站。
> 原因：**OSM 里大量中国地铁站是以 way / relation（站厅面）存储的**。
> 改成 `nwr[...]` + `out center` 后拿到 **556 站**，中文站名覆盖率从 57% 跳到 **100%**。
> 你手上的 `osm_st3.json` 已经是修好的版本。
>
> **发现方法**：拿到的站数和常识对不上（295 vs 523）就要停下来查，
> 而不是接受"匹配率 57%"这个结果。

## 3-2 · ⚠️ 坐标系是硬约束（坑 7）

```
两个数据源的站点要关联。先不要写匹配逻辑，先做一件事：
对 stationInfo.csv 的每个站点，在 osm_st3.json 里找最近的站点，
计算偏移向量 (dx, dy)，单位米，输出 dx 和 dy 各自的中位数与标准差。
根据结果判断两者是否同一坐标系，并说明你的判断依据。
```

> ✓ **验收**：**dx、dy 的中位数都在 ±2 m 以内**（具体值取决于你怎么给 OSM 站点去重），
> 标准差 30 m 量级。中位数接近 0 → 确认同为 WGS-84，可以直接匹配。
> 记住这个量级：**如果是坐标系问题，中位数会是几百米，不是几米。**

> ⚠️ **坑 7 · GCJ-02 火星坐标**
> 中国的数据集常用 GCJ-02（火星坐标），OSM 是 WGS-84，上海两者差约 **500 米**。
> 不查就按 400m 阈值匹配，会大面积匹配失败，还找不到原因——
> 你会以为是匹配算法写错了，改一下午的代码。
>
> **判据**：
> - 中位数接近 0、标准差小 → 同一坐标系，直接匹配
> - **中位数显著非零、标准差小 → 系统性坐标系偏移，必须先转换**
> - 中位数接近 0、标准差大 → 坐标系相同但数据质量差，要逐个看

## 3-3 · ⚠️ 线路归属与时代错置（坑 8）

```
从 osm_raw.json 里提取地铁线路：每条线路的 ref、官方 colour、以及 way 成员的几何。
再把 relation 里 role 以 stop 开头的 node 成员坐标收集起来，
用 400m 阈值给 stationInfo 的 302 个站做线路归属（一个站可以属于多条线）。
做完先报告：每条线路匹配到多少站，以及有多少站一条线都没匹配上。
```

> ✓ **验收**：线路归属覆盖率 **302/302 = 100%**。**然后停下来，看下一条。**

```

有哪几条线的数量明显不对？告诉我你的判断和原因，先别改代码。
```

> ⚠️ **坑 8 · 时代错置**
> 客流数据是 **2017 年**的，OSM 是**当前**的。
> 现网 14 / 15 / 17 / 18 号线经过 2017 年就已存在的老站，坐标匹配会把这些线路也算进去——

```

> 1→28、2→31、3→29、4→26、5→11、6→28、7→33、8→30、9→27、10→32、11→38、12→32、13→22、16→13。

# 附录 A · 出错时的「精准修正」话术

> 不要说"这里不对，重做一下"。那会让 AI 推倒重来，把已经对的部分一起改坏。

**A1 · 定位再修**

```
<某张图>的数据/显示不对，具体现象：______。
请先定位是数据筛选、聚合口径还是图表配置的问题，
只修改相关部分，并用一句话说明你改了什么、为什么改。
```

**A2 · 独立方法验证**

```
这个结果看起来是对的，但我不放心。
帮我设计一个独立的校验方法（不要用生成它的同一套逻辑），
验证它到底对不对。
```

**A3 · 追问数字的意义**

```
你刚才说"匹配成功率 57%"。这个数字是高是低？和什么比？
如果偏低，先别改代码，先告诉我可能的原因有哪几种，
以及每种原因怎么用数据验证。
```

**A4 · 拦住静默丢数据**

```
这一步做了筛选/关联/聚合。告诉我：
输入多少条、输出多少条、丢了多少条、丢的是哪些、为什么丢。
如果你没法回答"丢的是哪些"，说明代码里缺一个日志，先补上。
```

**A5 · 拦住"应该没问题"**

```
你说"应该没问题"。给我一个可以证伪它的检查：
一个具体的数字，我一眼就能看出对不对。
```

# 附录 C · 学员常见翻车点

| 现象 | 真正的原因 |
|---|---|
| 双击 `index.html` 打开是白屏 | 没起 http server，跨域读不到 `data.js` |
| 图表不显示但控制台没报错 | 容器 div 高度是 0，ECharts 画在了 0×0 的画布上 |
| 切页后图表变形 | 隐藏时 resize 了，见坑 5 |
| 海口轨道覆盖排全国第一/最后 | 空值被 `fillna(0)` 了 |
| 地图上北京"最绿" | 指标方向没做，见坑 4 |
| 站点匹配率只有一半 | 先量偏移中位数，判断是不是坐标系问题，见坑 7 |
| 某条线只匹配到 1 个站 | 时代错置，见坑 8 |
| 聚合出来的宽表行数是个怪数 | 某个维度的基数算错了，见坑 9 |
| KPI 卡数字和报告对不上 2.5 个点 | 口径，见坑 2 |
| 改了一个小地方，别的图全坏了 | 一次改太多，用附录 A1 的话术让 AI 只改相关部分 |

> **这门课想传达的一句话：**
> **Vibe Coding 的关键能力不是让 AI 写得快，是让 AI 的产出可被验证。**
>
> 九个坑全都不报错、肉眼也看不出来。
> 抓住它们靠的不是更仔细地读代码，而是每一步都设一个能证伪的断言——
> 行数对不对、总量能不能反算、两种独立方法一不一致、和外部已知数字合不合。
